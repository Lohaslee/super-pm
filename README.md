# Super PM

这个需求是真的吗？用户为什么要放弃现在的做法？如果只能做好一件事，应该是什么？又有哪些东西看起来很诱人，但这次坚决不能做？

这些问题，我自己做产品时也反复遇到。AI 可以很快列出功能、写出 PRD，却不一定能陪我把产品真正想明白。有时文档越完整，一个没被验证的假设反而越像事实。

后来我想到，自己这些年了解和学习过几位很厉害的产品大师。面对同一个问题，他们会从哪里追问，会做出什么取舍，又会因为什么改变判断？我想把这些不同的产品视角整理到一起，让它们真正参与需求讨论，而不只是留在书摘和笔记里。

`super-pm` 就是这样做出来的。它不是替你写文档、管流程或堆术语，而是陪你分析需求、拆开事实与假设、讨论取舍，把一个模糊想法慢慢收敛成可以验证、可以交付的产品方向。

它最初是为独立开发者验证 0→1 想法而做的，也能用来诊断已有产品。软件、AI、硬件、服务、内容、平台、企业产品和线下体验都可以讨论。希望它也能在你准备动手做产品时，帮你少走一点弯路。

## 能做什么

- **探索与判断分开**：想找新方向时，先比较机制不同的可能性及代价；问要不要做时，直接给建议。同时要求探索、推荐和简报时，按依赖顺序一起交付，无需先选模式或老师。
- **负向边界优先**：沿用已知边界；只有缺失边界会改变判断时，才追问不能接受的结果、本次不做的功能、硬约束和必须保护的产品品质。
- **区分事实与假设**：分开记录用户原话、事实、推断、建议和待验证假设；会改变推荐或显著影响成本、风险的假设必须明确说出。轻量核验不强制展示整张账本。
- **动态组织产品视角**：每个决定只设一个主责视角，其他视角只有能提出不同方案或关键风险时才加入。
- **允许指定主 PM**：你可以选择一个视角负责整体方向，其他视角补充和挑战，但最终仍以用户边界和可信证据为准。
- **适配不同产品类型**：按问题选择需求与价值、产品系统、使用与交付、触点与形态、体验与信任等维度，不机械套固定框架。
- **先验证高风险假设**：给出最低成本验证，说明阈值依据与样本限制；沿用你已经给出的研究或执行授权，只对超出范围的动作再确认。
- **按需沉淀产品决定**：高价值决定收敛时会提议一次是否保存；只有你授权后才写入 `.super-pm/decisions.md`，方向改变时保留被替代的历史决定。
- **知道什么时候退出**：纯工程实现只确认必要的产品约束后就进入开发；法务、税务、审计和专业财务结论会交给相应专业能力，不硬套产品视角。
- **随时输出简报、报告或 PRD**：独立开发与早期对齐可用一页决策简报；方向收敛后可产出供 AI coding agent 或团队直接开发的完整 PRD。
- **原则数量不凑数**：每个视角按资料深度独立沉淀，不设统一条数；重要回答可以用一句最相关老师的原话点题，但不会机械轮流发言或把金句当结论。

判断问题默认用一个尽量短的决策循环：说清问题，给出建议，保留真正影响判断的反对意见，检查负向边界，需要时再确定下一步验证。只有进入开发、跨多个产品维度，或面对昂贵、不可逆、安全及合规决策时，才展开完整定义。

## 七个产品视角

七套产品经验以化名呈现。它们是判断问题的方法，不是真人模拟，也不会为了凑人数轮流发言。其中“师母”在这里特指一套产品视角的化名。

| 视角 | 主要关注 |
|---|---|
| 乔帮主 | 聚焦、取舍、完整体验、产品品质与叙事 |
| 龙哥 | 人性、克制、自然交互、注意力与社交压力 |
| 梁老师 | 用户状态、情绪驱动力、真需求、系统能力与机会判断 |
| 俞老师 | 用户价值、替换成本、交易结构、优先级与假设验证 |
| 师母 | 本质思考、一手用户洞察、突破机制、内容与推荐产品 |
| 想哥 | 产品定义、核心体验、商业闭环、组织与规模化 |
| 军哥 | 时机、专注执行、性价比、口碑、用户参与与复盘 |

不同意见会被保留下来，再依据用户边界、事实证据、用户价值、交付能力和可逆性做出取舍。对话偶尔会自然带出不同视角的表达方式，但不会冒充真人、编造引语或暗示任何老师为具体产品背书。

## 语言与输出

- 默认使用简体中文；用户主要使用英文时自动切换为英文。
- 中英文资料独立维护，只加载当前语言所需的内容。
- 支持英文和中文控制：`Keep it brief` / “简短一点”只改变篇幅；`Back to normal` / “恢复正常”恢复深度；`Stop playing` / “别玩了”关闭主动彩蛋，恢复深度不会重新开启。
- 保留用户原有的产品名、指标和已确认原话，不擅自翻译。
- 表达专业但不堆黑话：内部推理完整，对外只讲影响决定的内容；适当保留有价值的老师意见和框架名并顺手解释，内部原则编号默认不展示。
- 保留轻量彩蛋：合适时用“只能留一个”帮助取舍，用“决定回放”呈现认识变化，或加一句老师提醒。一轮最多一种，不每轮出现；说“别玩了”或“直接给结论”后，本次对话停止主动趣味表达，直到你要求恢复。认真询问彩蛋机制时会直接解释。
- 报告和 PRD 是可选产物，不是讨论的默认终点。

## 安装

在 Codex 中输入：

```text
Install the skill from https://github.com/Lohaslee/super-pm/tree/main/skills/super-pm
```

安装完成后，通过 `$super-pm` 调用。

## 维护与版本统一

当前显式版本：**1.0.0**。版本号与来源写在 `SKILL.md` 的 `metadata` 中；更新见 [CHANGELOG](CHANGELOG.md)，行为验证状态见[覆盖记录](skills/super-pm/evals/coverage.md)。历史未编号版本继续按提交号记录。

仓库中的 `skills/super-pm/` 是唯一维护源，包含彩蛋；已安装目录只作为同步目标，不分别演进。更新后先跑校验和受影响的行为用例，再同步到实际使用的安装位置并比较完整目录内容。不要仅凭描述中写了“彩蛋”就认定运行版本包含相关规则。

入口只保留日常分流与必要约束；完整产品流程、趣味互动和维护要求按需加载。结构校验检查文件与卡片完整性，不代表模型行为测试已通过。

只读检查本机两个标准安装目录；版本号相同也会比较完整内容：

```bash
python3 -B skills/super-pm/scripts/check_installation.py
```

显式加 `--upstream` 可查询 GitHub main；加 `--compare /path/to/installation` 可检查其他安装位置。不会自动更新；网络不可用显示未知，本地未提交内容单独标明。
